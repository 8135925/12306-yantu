# yantu · 沿途放票地图 — 需求文档

> **一句话定位**：选定一趟车，看清沿途每一站的放票进度，辅助"买长乘短 / 买短乘长+补票"购票决策。
>
> **部署目标**：Vercel（静态前端 + Serverless API）
> **版本**：v1.1 · 2026-09-22 · 前端技术栈调整为 React

---

## 1. 背景与问题

12306 在运能紧张时优先满足全程旅客，票额分时段向沿途站点动态投放。这导致：

- 用户查询"出发站→到达站"常显示无票，但同一车次"出发站→更远站"却有票；
- 12306 App 的车次详情页可以人工翻看各经停站余票，但**没有"一眼看完全程放票地图"的视图**，更没有放票进度的持续监控；
- 现有开源工具（py12306、Bypass 等）聚焦自动下单，均无"逐站放票可视化"能力。

**yantu 填补的空白**：不做自动下单（规避账号风控与合规风险），只做**放票信息的查询、可视化与监控**。

## 2. 用户故事

| # | 作为… | 我想要… | 以便… |
|---|---|---|---|
| US-1 | 买不到直达票的旅客 | 选定车次后看到沿途每一站的余票状态 | 判断"买到更远的某站、在目标站下车"是否可行 |
| US-2 | 短途旅客 | 看到哪些中间站已放票 | 先买到最近的有票站上车，越站区间补票 |
| US-3 | 盯放票的用户 | 页面自动刷新，放票时立刻看到 | 分时段抢投放的新票额 |
| US-4 | 移动端用户 | 手机浏览器直接访问 | 无需安装 App |

## 3. 功能需求

### F1 站点字典与选择器（阶段一 · ✅ 本次交付）

| 编号 | 需求 | 验收标准 |
|---|---|---|
| F1-1 | 站点字典生成 | 构建脚本从 12306 `station_name.js` 解析全国车站，输出 `public/stations.json`，含站名/电报码/全拼/拼音缩写/城市归属五字段；站数 ≥ 3000，异常（< 2000）时构建失败 |
| F1-2 | 出发站/到达站选择器 | 可搜索输入框，支持站名（如"上海"）、全拼（`shanghai`）、拼音缩写（`sh`）三种匹配；联想列表按城市分组，上限 30 条 |
| F1-3 | 键盘交互 | ↑↓ 移动高亮、Enter 选中、Esc 关闭联想 |
| F1-4 | 选中产物 | 选中后页面展示站名 + 三字电报码（如 上海虹桥 `AOH`）；支持出发/到达互换 |
| F1-5 | 字典即约束 | 用户只能从字典中选择（联想列表唯一来源），不允许自由文本直传查询接口 |

### F2 放票查询 API（阶段二）

- Serverless 函数 `api/query.py`（Python，复用已验证的查询链路）：
  入参 `date, train, from(电报码), to(电报码)`；
  1) 余票查询定位车次 → 取 `train_no`；2) `queryByTrainNo` 取全程经停站；
  3) 从实际出发站起逐站查"出发站→该站"余票（并发池 5、间隔 0.3s）；
  4) 返回 `[{station, arrive, depart, seats:{二等座:"有"/"无"/数字/…}}]`。
- 服务端校验 from/to 电报码必须存在于 `stations.json`（不信任前端）。
- 12306 接口适配要点（已实测）：先访问 `/otn/leftTicket/init` 取 cookie；`/query` 302 跳动态端点（queryG/queryU…）需手动跟随；席别索引为新版正索引（二等30/一等31/商务32/硬卧28/硬座29/无座26…）；`queryByTrainNo` 不含电报码需查表换码。

### F3 放票地图展示（阶段三）

- 视图 A · **站点时间轴**：横向经停线 + 每站徽章（绿=有票 / 红=无 / 黄=候补 / 数字=余票量）；
- 视图 B · **站×席别矩阵**：行=经停站，列=席别，状态着色；
- **买长乘短高亮**：从目标站向终到方向，第一个"有票区间"自动标注为建议购票区间；
- 12306 官方规则提示：允许票面区间内的中途上车/下车，买长乘短合规、多买部分不退票。

### F4 监控与缓存（阶段四）

- 前端轮询开关：15–30s 自动刷新，放票变化时视觉提示；
- CDN 缓存：查询结果 `s-maxage=15`，同车次多用户共享缓存；
- 限流：每 IP 每分钟 5 次查询（防刷函数配额与 12306 风控）。

### F5 部署与运维（贯穿）

- 平台：Vercel，函数 region `hnd1`（东京）；
- `vercel.json`：站点字典长缓存（已配置）、函数 `maxDuration=60`（阶段二配置）；
- 站点字典更新：手动重跑 `scripts/gen_stations.py` 提交（低频变更，暂不做自动更新）。

## 4. 非功能需求

| 类别 | 要求 |
|---|---|
| 性能 | 单车次（≤30 站）查询 ≤ 3s（并发池）；页面 LCP < 1.5s（静态资源 + CDN） |
| 成本 | 站点字典走静态 CDN 零函数开销；Hobby 免费额度内可运行 |
| 合规 | 仅查询公开数据、无登录态、不下单、不代购；README 声明"仅供学习研究，遵守 12306 服务规则" |
| 风险 | ① 12306 接口字段变更 → 席别映射集中在单文件，改一处生效；② 海外 IP 风控 → 备选方案：腾讯云 SCF 做国内查询代理层；③ 字典漂移 → 构建时校验站数下限 |

## 5. 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 前端 | React 18 + Vite（TypeScript） | 组件化管理选择器/时间轴/矩阵等交互视图，状态清晰、易扩展 F3/F4 的轮询与高亮逻辑；Vite 构建产物仍为静态资源，部署方式不变 |
| UI 样式 | 原生 CSS / CSS Modules | 页面轻量，不引入重型组件库 |
| 站点字典 | 自研构建脚本生成静态 JSON | 3388 站 272KB，CDN 直出；未选 npm 包 `china-railway-station`（GPL-3.0 协议顾虑 + Python 侧无法复用） |
| API | Vercel Python Serverless | 复用已实测的 Python 查询脚本 |
| 站点选择器 | React 自研 combobox 组件 | 需求简单（匹配+分组+键盘），用受控组件实现即可，无需引组件库 |
